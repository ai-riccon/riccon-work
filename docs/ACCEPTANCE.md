# 产品验收

本文件记录两层验收：

1. **Product 预验收**：实现是否按 `docs/PRODUCT.md`、UX 设计和范围落地；
2. **用户最终验收**：用户是否接受这个用户可见结果。

它不是 Verifier 的模块 review，也不是发布批准。Verifier 负责独立验证 AC、安全和行为；Product 不能替代 Verifier，用户保留最终接受权。

### Product 结论与建议

- **结论：`changes-requested`**。M06 的 23 条 gate AC 中 17 条 `pass`、5 条 `pass（with residual）`（AC-14/16/18/21/23）、AC-17 `fail`；另有 AC-11/25 为 M06b/M26 N/A。未发现新的 P0/P1 安全或功能绕过；但 AC-17 是 P0 用户可见 AC，F-001 不是纯打磨，且修复成本小，因此 Product 不采“无条件 pass with residual”，要求 small fix 后复核。F-002 是 PII/安全决策，Product 不接受当前 A 方案，必须由用户/安全明确选择后才能进入用户最终验收。
- **F-001 裁决（changes-requested）**：AC-17 明确要求“限制值在界面可见”和“超限提示具体限制/当前值/下一步”；服务端 enforcement、稳定码和 5 MiB 文案已通过，但 Web 无 limits 读取/展示，429 文案无具体数值。该缺口是 P0 AC 的用户可见完整性缺口，不是环境问题，也不是纯 P3 文案；在现有 `GET /workflows/runtime-limits` 基础上做只读视图/帮助浮层并补 429 文案即可，建议 owner `riccon/builder-b3` + `riccon/verifier`，due M06 done 前，重跑相关 Web/E2E 证据，不新增 AC。
- **F-002 裁决（open decision）**：Product 推荐 **B：审计只存 `commentSha256`，理由保留在审批记录**；理由是审批理由是用户自由文本，可能含 PII，审计 180 天且可导出，最小化更稳妥。若业务坚持 **A：理由入审计**，必须由用户 + 安全明确接受并记录，Product 不替用户接受安全风险；当前实现 A 不视为 U-05 已解决。owner `riccon/lead` + 安全/Architect，due 用户最终验收前（优先 M06 done 前）；若选 B，需 small fix + 测试。

## 规则

- gate 检查通过后、模块标记 done 前，先完成 Product 预验收；Product 未 `pass` 前不能把模块标为 done。
- 模块 done 后再提交用户最终验收；用户未 `accepted` 前，不进入下一个用户可见模块；最终产品验收未 `accepted` 前，不进入生产发布。
- 用模块的 `product_acceptance` 记录两层结论：`product_status` 和 `user_status`；本文件保留详细 AC 表和证据。
- 验收失败用 `kind: fix` + `fixes_module` 建修复模块，或在显式决策后重新打开；不要只靠标题或 `depends_on`。
- `rejected`/`conditional` 必须列出条件、截止时间和后续任务。
- 验收结论不替代 gate、release check 或生产批准。
